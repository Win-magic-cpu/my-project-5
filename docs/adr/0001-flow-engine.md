# ADR 0001：自研 YAML Flow 引擎，而不是 LangGraph

- 状态：已采纳
- 日期：2026-10

## 背景

任务型对话（查订单、查物流、退款申请）的步骤是稳定的：收集槽位 → 调用业务接口 →
组织回复。早期版本把这些步骤写成 `if step == "ask_order_number": ...` 的硬编码状态机，
每加一条业务流程都要改代码、发版、回归。

同时期可选方案是 LangGraph 这类通用编排框架。

## 决策

自研一个约 400 行的 YAML Flow 引擎：

- 5 种 Step：`start` / `collect` / `action` / `response` / `end`
- `next` 支持直接跳转与 `if/then/else` 条件跳转
- `collect` 自带 Slot 校验与"用聚焦对象补槽"
- 业务动作通过 `Action` 子类扩展，启动时扫描 `custom/` 包自动注册

## 理由

1. **语义比通用框架窄**。我们只需要顺序推进 + 条件分支 + 槽位校验，不需要图、并行、
   子图、检查点。窄语义意味着代码可读、出错可定位。
2. **错误处理可控**。Step 执行失败时，我们明确知道该停在原地等待用户、还是结束任务；
   通用框架的异常语义需要额外适配。
3. **可测试**。FlowExecutor 是纯函数式的状态推进，单测覆盖 5 种 Step 和条件跳转，
   不需要起服务、不需要 LLM。

## 代价

- 不支持并行分支与循环（用 `max_steps_per_turn=100` 兜底成环配置）
- 没有可视化编辑器，运营改流程要改 YAML 并重启
- 条件表达式基于受限 `eval`，复杂逻辑仍需写 Action

## 备选方案

| 方案 | 为什么不选 |
| --- | --- |
| 硬编码状态机 | 每加流程都要改代码，和"配置化"的目标相悖 |
| LangGraph | 抽象过重，调试链路长；当前需求用不到图能力 |
| 规则引擎（如 durable rules） | 引入新 DSL，团队学习成本高于收益 |
