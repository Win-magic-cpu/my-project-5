# ADR 0002：计划生成与计划校验分离

- 状态：已采纳
- 日期：2026-10

## 背景

用户消息要变成动作，中间必须经过"理解"。最初的做法是让 LLM 直接输出动作并执行，
线上很快出现三类问题：

1. 模型编造不存在的 Flow / Slot 名称；
2. 一句话同时命中"查订单"和"问政策"，系统只执行了其中一个；
3. 意图需要商品上下文，但用户还没选商品，模型硬答。

## 决策

拆成两个阶段：

- `TurnPlanner`：只负责把自然语言翻译成 `TurnPlan` JSON（task / knowledge / chitchat）；
- `TurnPlanValidator`：用**纯代码**校验计划能否执行，不通过就交给 `ClarifyResponder`。

校验内容：方向是否唯一、Flow 是否存在、命令顺序是否合法（按顺序模拟任务状态）、
Slot 名是否在白名单、知识意图所需对象是否具备。

## 理由

1. **职责匹配**：模型擅长理解，不擅长保证"可执行"；后者是确定性规则，应该用代码写。
2. **可测试**：8 条拒绝规则每条都有单测，不依赖模型输出。
3. **可解释**：校验失败会给出明确 `ClarifyReason`，澄清话术可以针对性生成。

## 代价

- 多一次 JSON 解析与规则执行（毫秒级，可忽略）
- 规则需要随业务演进维护（新增 Flow 时 Slot 白名单自动来自 FlowCatalog）

## 备选方案

| 方案 | 为什么不选 |
| --- | --- |
| 让模型自己判断能否执行 | 模型没有系统状态的权威视图，且无法保证稳定 |
| Function Calling 直接执行 | 参数错误会直接产生副作用，缺少拦截层 |
| 只做 schema 校验 | 只能保证格式，保证不了业务可执行性 |
