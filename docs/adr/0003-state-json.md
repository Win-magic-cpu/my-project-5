# ADR 0003：对话状态整份 JSON 存储 + 乐观锁

- 状态：已采纳
- 日期：2026-10

## 背景

一次对话的状态包含：当前会话、历史轮次、聚焦对象、活动任务、暂停任务。
多轮对话要求跨请求保持，因此必须落库。

## 决策

- 每个用户一行：`dialogue_states(sender_id PK, state_json TEXT, version INT, updated_at)`
- 用 pydantic `TypeAdapter` 完成 dataclass 与 JSON 的双向转换
- 写入用乐观锁：`UPDATE ... WHERE version = 读到的版本`，影响 0 行抛冲突，Service 重试

## 理由

1. **读写模式简单**：一次请求只读写一个用户的一行，没有 join。
2. **演进成本低**：状态结构变化只影响序列化层，加字段靠默认值兼容；表结构变化用 Alembic。
3. **不锁 LLM 等待**：状态是整块 JSON，行锁会把模型 5 秒的等待也锁进事务；
   乐观锁只在写入瞬间校验版本，冲突概率低。

## 代价

- 跨用户分析能力弱（"昨天有多少人卡在退款流程" 需要额外导出/解析）
- 单行会随会话增长（当前用"会话超时 + 只保留最近消息 ID"控制）
- 冲突时需要重跑一遍引擎（可能多一次 LLM 调用），用幂等窗口避免重复记录

## 备选方案

| 方案 | 为什么不选 |
| --- | --- |
| 拆成 sessions / turns / tasks 多表 | 查询能力强，但一次请求多次 join，写入事务复杂 |
| Redis 存状态 + 定时落库 | 引入缓存一致性问题和额外组件 |
| 事件溯源（append-only） | 适合审计，但当前读取路径会变复杂 |
