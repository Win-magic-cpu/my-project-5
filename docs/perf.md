# 压测报告

> 目的不是刷一个漂亮数字，而是回答两个问题：**应用层能扛多少？瓶颈在哪？**

## 环境与方法

| 项 | 值 |
| --- | --- |
| 机器 | Windows 11，本地开发机 |
| 服务 | 单进程 uvicorn，1 worker |
| 存储 | SQLite（`data/perf.db`，写串行） |
| 模型 | `tools/mock_llm`（单进程，确定性返回） |
| 压测工具 | `perf/load_test.py`（httpx + asyncio，零额外依赖） |
| 请求 | `POST /api/chat`，`text="你好"`，每个虚拟用户独立 sender |

```powershell
uv run python perf/load_test.py --all          # 5 / 20 / 50 并发
uv run python perf/load_test.py --mode health --concurrency 50 --total 500
```

## 结果

### 对话链路（planner → 校验 → 闲聊 → 落库）

| 并发 | 请求数 | 耗时 | RPS | p50 | p95 | p99 | 错误率 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 5 | 100 | 1.81s | 55.2 | 71.7ms | 156.6ms | 323.0ms | 0% |
| 20 | 200 | 3.66s | 54.6 | 207.8ms | 835.8ms | 2328.4ms | 0% |
| 50 | 300 | 5.49s | 54.7 | 717.1ms | 1457.5ms | 3133.3ms | 0% |

### 应用层基线（`GET /healthz`，50 并发）

| 请求数 | 耗时 | RPS | p50 | p95 | p99 | 错误率 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 500 | 0.61s | 818.2 | 57.8ms | 93.9ms | 112.1ms | 0% |

## 结论

1. **应用层不是瓶颈**：`/healthz` 在 50 并发下 818 RPS，p95 不到 100ms，说明 FastAPI + 中间件 + 请求解析开销很小。
2. **对话链路卡在 ~55 RPS**：并发从 5 涨到 50，吞吐几乎不变（55.2 → 54.7），延迟却线性上涨（p50 72ms → 717ms）。这是典型的**下游排队**：请求越堆越多，单次处理被拉长。
3. **两个上游各占一半**：
   - mock LLM 是单进程 uvicorn，且每次对话至少一次 `/chat/completions`，它自己就是串行队列；
   - SQLite 写操作串行，50 并发时每个请求都要排队等写锁。
4. **没有错误**：50 并发 300 请求 0 失败，说明 `sender_id` 锁、SQLite busy timeout（30s）、状态保存都没有互相打架。

## 怎么优化（按性价比排序）

| 优化 | 预期效果 | 代价 |
| --- | --- | --- |
| uvicorn 多 worker / 多实例 | 应用层线性扩容 | 需要把 sender 锁换成 Redis |
| 换 MySQL（已提供 compose） | 去掉 SQLite 写串行 | 运维成本 |
| 给 LLM 调用加连接池/超时/重试上限 | 避免排队无限放大 | 需要限流策略 |
| 流式返回（已实现） | 首字延迟下降，体感变快 | 吞吐不变 |

> 注意：本次压测用的是 mock 模型，数字衡量的是**应用与编排开销**，不代表接真实大模型后的表现（真实场景首 token 通常 0.5~2s，瓶颈会完全转到模型侧）。

## 局限

- 单次采样，数字有 ±10% 波动；
- 单机、单进程，没有跨机器网络开销；
- 没有压流式接口（流式需要按 token 计时，指标口径不同）；
- Docker 镜像未在本机实际构建（Docker Desktop 守护进程未启动），只做了 `docker compose config` 校验，构建留给有 Docker 的机器或 CI。
